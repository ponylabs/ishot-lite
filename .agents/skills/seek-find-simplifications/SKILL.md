# 寻找可证明的简化

简化的尺度是长期需要维护的责任减少，而不是删除行数。先查实际架构、现存决策及兼容范围；有明确理由保护的设计，不能因为看起来复杂就移除。

## 建立候选

沿生产入口追踪“产生者 → 转换 → 消费者 → 可观察效果”。优先回答：

- 某个区分是否真的改变消费者动作？是否只是被一路传递？
- 能否从权威来源读取，删除副本、缓存失效、历史索引和同步机制？
- 更窄且明确的能力是否足够？若会丢能力，先写清损失并取得相应确认。
- 抽象是否聚合共同机制，还是把不同策略隐藏到更多间接层？
- 替代库是否真正删除维护责任，还是新增适配、生命周期及打包负担？

搜索符号、读写点、事件字符串、配置键、清单、公开导出、生成入口及动态加载。没有静态调用不能证明公开 API 无人使用。把候选分为可证不可达、接受能力收缩后可删、受约束保护、证据不足。

## 做出取舍

每个值得实施的候选说明当前所有者、调用链、删除与剩余成本、兼容影响，以及最强的保留理由。只搬到另一文件、另一层或者依赖里不算简化。

跨所有权或信任边界的复制、校验可能必要。异步标志、Promise、取消状态可能承担终态仲裁、停机排空或持久化保障；先说明这些责任如何保留。替换依赖时检查限制、取消、截断、打包，以及源码运行与构建产物差异。

## 实施与验收

只处理授权范围，先建立可观察行为证据，再做最小替换。证明行为保持，或者验证已明确接受的收缩。重大取舍才记录长期决策，先检查已有记录是否应更新；不要为每次删函数新建文档。

输出落地结果、验证、拒绝的候选及重要待定项。无法解释剩余生命周期或兼容性时停止该候选，保留明确问题，不以“后面补测试”作为依据。
