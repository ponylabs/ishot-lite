# 页面表达与导航

遵循现有格式拥有者；以下是读者导向的默认选择，不是要求每页出现同一组标题。

## 从入口到细节

长篇人工文档先用短段落说明读者能做什么、为什么需要、基本运行方式和最重要限制，再按篇幅增加目录。主要章节在表格、代码或子节前用一句话说明主题与决策点，不复述全节。正文依次展开基本用法、进阶选择、维护者设计；用户入口不堆函数名和内部事件流，除非它们就是公开配置或 API。

概念级实现说明保留组件关系、数据流、生命周期和维护陷阱，精确字段/API/类型清单链接源码或生成目录。大量生成内容用简短入口与稳定索引，只有独立领域拥有者存在时再拆分。相邻探索链接按前提到深入排序，说明各自用途；通常少量直接相关链接就够，不做全站目录。

## 清楚、准确的中文与英文

明确执行者和动作，一概念一术语，优先直接动词。每句一条主要指令，多个步骤或条件用列表；每段只讲一个主题。避免分号串联、空泛质量形容词和重复保留意见，但必须保留原有不确定性、必须/允许/禁止、数量、条件、时序和例外。

英文句长只能作为审阅提示，中文不套英文词数。不为了长度阈值切断条件关系，不声称符合未实际验证的受控语言标准。粗体用于改变行为的约束或关键比较，不让整页失去层次；代码标记用于准确标识，非装饰。

## 折叠与分隔（格式支持时）

长篇开发细节可用渲染器支持的折叠块；标题和稳定锚点留在外面，只折叠正文。GitHub 的 `<details>` 在 `<summary>` 后留空行，Markdown 不额外缩进，结束标签前留空行，并实际检查渲染。不得折叠用户安全操作所必需的前提、失败和限制。

水平线前后留空行，避免被解析成 Setext 标题；已有机器解析器依赖章节顺序时不插入破坏其结构的分隔。是否折叠、分隔符样式、最终章节顺序由目标项目决定，不继承上游的强制版式。

## 元数据与链接

描述说明文档覆盖什么、何时打开，含可检索领域词并区别相邻页面；不用广告、历史流水或全节摘要。名称由标题拥有、语言配对由工具拥有时不再重复；没有稳定分类和检索消费者就不新增标签。

内部链接使用当前渲染器可验证的相对路径，页内目录用锚点，外部资源用完整 URL。逻辑路径提及与可点击目标分开判断：GitHub 中以 `/docs/` 开头不一定指向仓库，不能因看起来像绝对路径就采用未验证链接。有站点时同时检查投影后的路由、锚点和资源，不只检查源文件存在。
