# 类型、归属与阅读路径

先问读者要完成什么，再决定文档形态。文件路径可以提供线索，最终分类必须由模块入口、配置、代码和目标读者共同确认。

## 类型选择

| 读者问题 | 主要形式 | 应有信息 | 不应混入 |
| --- | --- | --- | --- |
| 这是什么，如何开始 | 根 README | 用途、最短安全入口、状态和深入链接 | 全部内部实现与任务流水 |
| 如何完成一个具体操作 | 操作指南 | 前提、顺序、精确输入、结果、失败恢复 | 穷举 API 字段 |
| 我需要系统学习某项能力 | 教程 | 从已知到未知的概念、练习和检查点 | 无解释的参数全集 |
| 某模块允许怎样使用 | 模块 README 或参考 | 职责、入口、配置、行为、失败、限制 | 其他模块拥有的契约副本 |
| 模块之间怎样协作 | 架构说明 | 责任、关系、数据流、状态归属、扩展点 | 逐行重述代码 |
| 为什么做出这项长期选择 | 决策记录 | 背景、可行替代、取舍、后果和证据 | 尚未决定却装作已接受的方案 |
| Agent 在这里必须遵守什么 | 根/子 AGENTS | 作用域内必要约束、事实与 Skill 入口 | 完整工作教程、业务说明副本 |
| 精确枚举 API 或字段 | 生成参考 | 可追溯源、稳定索引、生成和检查方式 | 手工维护另一份易失真清单 |

先复用现有拥有者。一个页面同时承担大量操作教程和穷举参考时，按实际读者任务分开；不能仅因长就随机分割。只有独立负责人、更新节奏、引用需求或验证方式确有差异时，才新建小文件。紧密关联的一项义务应放在一起。

## 分层职责

根入口负责全局导航，模块 README 就近记录模块契约，子 AGENTS 只记录相对父层新增的局部约束。跨模块关系放在 `docs/architecture.md`，独立专题按 [文档契约](../../../../docs/AGENTS.md) 条件创建。六个固定入口始终保留，不强制业务代码目录。父级索引解释该组内容的作用，再链接直接下级，不复述每页规则。具体测试清单不是架构图的一部分：架构页保留验证责任与导航，执行命令从项目实际配置获取，局部机制留在其拥有层。确需穷举时优先从权威源生成并检查新鲜度，不手写第二份目录。

项目源码、配置和生成器提供可执行事实，测试提供已执行路径的证据，当前决策记录提供设计依据。旧 README 或讨论不能自动胜过当前实现，但实现偏离已确认契约时也不能未经确认将契约改成现状。

## 读者深度

常见阅读路径按以下顺序组织，按需要选取而非机械建立章节：

1. 用户可观察的能力、何时使用或避免使用。
2. 前提、最短安全用法、可观察成功和主要失败恢复。
3. 配置选择、限制、集成与运维行为。
4. 给维护者的状态归属、生命周期、错误、性能或安全边界及代码入口。

开发说明解释组件如何协作，链接源码承载精确细节；折叠区也不能成为 API/字段枚举和 JSDoc 的副本。穷举参考保留紧凑入口和索引，避免一次查找被迫扫描无关领域。

页首先回答读者能做什么，不以内部类名、注册流程或泛泛赞美开场。较长页面添加真正有用的目录；较短页面不强制目录。实质章节先用简短文字定位，再给表格或示例。可增加少量直接相关的下一步链接，不复制站点全索引。

## 检索元数据

只有现有索引、宿主或检查器实际使用时才引入统一元数据。description 应说明涵盖什么、何时该读，使用明确领域词，不堆章节摘要或宣传语。名称已由标题/清单拥有时不再复制；不要在无消费方时引入 tags、kind 或状态清单。

若项目采用类型到模板的机械映射，新增类型应同时明确模板、事实归属与针对性检查。不能只新增 kind 名字却没有消费者。现有机器格式、历史记录和生成片段遵循自身 parser；记录例外而不是生成无效格式。
