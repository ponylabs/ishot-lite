# 文档审查与验证

以读者是否能完成目标判断文档质量，不以章节是否填满或字数是否减少判断。

## 两遍审查

第一遍查正确性：目标读者、前提、入口、结果、状态归属、失败、恢复、限制、修改点是否有证据。第二遍查组织：是否先给常见路径，详细解释是否在其拥有者处，是否重复维护，标题和术语是否便于检索。

一个不了解仓库的专业工程师应能经过少量相关入口回答：它做什么、怎样安全运行、状态在哪里、谁负责、如何失败、从哪里修改。三至五个相关页面可作为审查提示，不是必须创建的文件数量。若必须读源码才知道公开操作流程，应补说明；若必须吸收无关内部实现，应调整层次。

## 规模与文档爆炸

先检查整个授权范围的结构，再处理句子。用搜索定位重复规则、手写清单、实现后仍存在的计划、调试叙事和状态流水。新增或删除模块、测试、命令时，搜索其名称及旧称在活跃文档中的出现位置，逐项判断是必要使用契约、导航，还是源码/配置已拥有的清单副本；链接仍有效不能证明这份清单完整或最新。逐项选择保留、归并、迁移、删除、补充或暂缓，不以删字数量作为 KPI。

关注一次查找需扫描的无关内容、入口路径、最大章节、标题数量和页面体积。只有已有独立领域拥有者时才据此拆分，不为满足长度提示造出大量小文件。一个解释一个主要位置，使用处保留必要短契约。

若项目已有预算，依次尝试调整归属、压缩重复、最后论证是否需要变更预算。预算是异常提醒，不是删减目标；不得为消除失败删除条件、限制或证据。删除文字若改变对外承诺，必须作为行为变化处理，而不是包装成润色。

## 按变更选择验证

| 改动 | 必要证据 |
| --- | --- |
| 使用指南、命令和配置 | 当前版本的精确操作与可观察结果；不能运行时明确责任和缺口 |
| 模块 README 或接口说明 | 入口/配置/行为对应的源码、调用方和测试；操作示例仍需运行 |
| 文档移动或重命名 | 入链与消费方搜索，相关渲染/路由/锚点检查 |
| 生成参考 | 源头修改、重新生成、确定性或新鲜度检查 |
| 多语言（已存在） | 受影响语义、术语、链接和既定配对检查 |
| Skill 或 AGENTS | 宿主格式/路由检查和代表性实际 Agent 场景；格式通过不代表遵循 |
| 门禁或规则脚本 | 有效样本通过、无效样本经真实检查入口拒绝，并确认 CI 调用该入口 |
| 运行时文案、工具描述 | 对应实际消费者场景或行为测试，不能只跑 Markdown 检查 |

先在局部迭代，完成后运行本项目实际适用的文档、格式、生成和行为检查，确认预期文件/测试确被选择。未运行、失败和通过分别报告。全量空白检查、CI 和业务测试各证明不同内容，不能相互替代。

## 必须考虑的负例

- Linux 执行成功，却在文档中承诺 Windows 也通过。
- README 移动后，AGENTS、参考式链接或站点清单仍指旧路径。
- 将有取消和资源等待要求的说明压成“停止并清理”。
- 修改生成的字段清单，不修改真正的 schema。
- 拿检查器单元测试通过当成实际 Agent 文档维护稳定。
- 初始化新业务项目后，CI 仍只运行模板文档检查。

这些是验收设计，不表示已经执行。实际场景应记录初始状态、操作、观察结果及限制，不将阅读规范当作测试通过。
