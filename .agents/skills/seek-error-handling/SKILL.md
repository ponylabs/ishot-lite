# 错误与恢复

处理异常前先说明什么失败、谁拥有状态、失败后还能保证什么。捕获只控制传播，不会撤销已发生的副作用。

## 失败身份

预期失败使用项目已有结构化约定：稳定类型或判别字段、处理所需细节和原始原因。机器身份与显示文本分开，不靠解析错误字符串分流。未知程序缺陷可以保留原始异常，但隔离层不能把它转换成成功。

## 状态与责任

每个失败路径明确处理者、报告者、隔离边界和清理责任，并分类副作用为未发生、部分发生、已提交或未知。后台任务同样需要这些保证，不能只打日志后丢失责任。

只有状态所有者能确认恢复后仍满足后续操作的前提。没有保证时停止依赖工作、废弃失效实例或升级报告。记录日志不等于恢复；catch-and-continue 必须解释安全继续的依据。

## 重试与监督

重试前确认安全重复或幂等机制，尤其结果未知时先核实状态。明确取消、次数/时间预算、退避和责任所有者。有限任务不能无限重试；持续监督需要生命周期所有者、停止方式与可见降级。失败分类与实际边界的政策决定是否重试，不把所有异常视为瞬时网络错误。

见 [失败场景](references/failure-cases.md) 的部分提交和报告失败案例。

## 可见报告

最终报告包含易懂摘要、受影响操作、结果/不确定性、系统当前处置和安全下一步。不能无依据声称成功、回滚完成或可安全重试。持续失效状态需要持续可见，不只闪现提示或默认关闭的日志。

有本地化机制时使用接收应用的机制；诊断沿用项目语言。避免向用户暴露秘密和敏感内部细节。报告自身失败需要独立后备通道，不能依赖同一个已坏的资源报告它自己。

## 验证

检查最终状态、外部副作用、清理完成和用户可见结果，不只断言异常被捕获。覆盖发生前失败、部分成功、结果未知、取消与恢复再次失败中实际相关的路径；无法安全测试的边界明确说明。
