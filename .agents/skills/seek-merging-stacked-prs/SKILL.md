# 依赖 PR 的集成

本流程不是合并授权。先确认目标仓库、主干、顺序、整个栈还是明确的底部前缀，以及允许的提交历史策略。合并、重写、强推、改 base、删除分支各自遵循用户授权和仓库规则。

## 建立当前依赖图

使用干净独立工作区，读取各 PR 的 base、head、精确提交、作者、跨仓库情况、草稿/开放状态、评审、未解决线程和 CI。实时元数据是依据，分支名和之前的报告不是当前事实。

若平台提供原生 stack 对象，验证工具和服务端能力及实际成员、顺序、完整分页结果；不能只用 base 链冒充官方成员身份。已有多个栈、额外成员、顺序冲突或跨 fork 限制时停下报告，不擅自解散重建。

项目规定原生栈时就使用受支持的原生操作；不可用则阻塞，不退回逐 PR 手工操作绕约束。项目未采用原生栈时，不凭借模板强制安装扩展或写死版本，也不臆造命令；先明确现有机制能否安全维护依赖。链接、重排和跨作者变更均需在授权范围。

## 更新与传播

不要仅因有刷新命令就改写历史。确需更新主干时，依现有策略自底向上 merge-forward 或执行受支持的 cascading rebase。先确认命令是否会立即推送所有层；若会，只有在授权覆盖该范围时才运行。

禁止无保护的强推覆盖并发远程改动。改写后重新获取精确 head，验证每一受影响层、未解决评论、审批有效性和 CI，不沿用旧 OID 上的就绪结论。冲突或本地远程成员分歧要保留现场并说明，不能自动删除远程结构。

## 合并前后

立即复核每层仍开放、非草稿、顺序正确且满足各自合并条件。顶层通过不代表底层通过。部分合并必须是明确边界之前的完整依赖前缀，不能跳过依赖。

使用项目支持的栈操作保留平台的检查、排序和队列语义，不绕过保护。请求入队不等于已经合并；直到选定 PR 各自报告已合并，才能宣称落地。剩余层检查 base、顺序、新 head、评审与 CI。

分支删除是独立末尾步骤：确认对应 PR 已合并，且没有开放 PR 仍以该分支为 base。任何状态不明都不删除。报告已合并、仍排队和受阻项，而不是笼统“完成”。
