# 编写可执行的升级说明

先检查本次差异是否改变已有未发布指南描述的行为，再判断谁会受影响。即使不再新增破坏性变化，也必须修订失效的迁移要求。纯内部接口且同一变更已迁移全部消费者，不必生成升级指南。外部兼容性破坏一旦识别，应在同次变更写清，不等发版后再补。

## 定位版本边界

按文档契约使用 `docs/upgrade-guide/v<版本>/<条目>/guide.md`，目录版本表示“从该版本升级”，不是目标版本；不建立根 README。再从项目真实版本来源确认“哪个已发布版本 → 哪个目标版本”。相同未发布边界的相关变化更新已有指南，不不断追加重复文件。若破坏性改动撤回，同步移除不再适用的未发布说明；已发布指南是冻结的历史事实，不按当前实现重写；更正或新迁移要求写入后续适用条目。

## 最少必要内容

默认两部分：

1. 变更：以前是什么、现在是什么、受影响的用户或调用方式，以及不受影响范围。
2. 迁移：按执行顺序列确切文件、键、命令或符号；前置条件、备份要求、动作和成功判断。存在数据风险、不可逆步骤或回滚限制时明确说明。

设计取舍放在其所有文档，不把指南变成架构论述。避免未确认的版本、模糊的“调整配置”和无需执行的长叙述。

## 验证

逐项对照真实公开变更和调用方；尽可能运行示例及升级路径，证明旧状态能到达可用新状态。数据迁移另需真实校验及恢复证据，不能因有指南就声称安全。无法验证时明确限制，不能假装已演练。

只在项目已有多语言政策时同步相应版本；不强加文档站、固定字数或某包管理器。
