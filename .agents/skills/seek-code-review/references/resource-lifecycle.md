# 资源所有权与停机顺序

从实际服务或插件入口追踪模块初始化、服务注册、监听器、计时器、子任务、进程、连接及传递调用。找出每个可变状态和资源的所有者及释放入口；不能因框架声明依赖就假定清理顺序正确。

## 查三类风险

1. 隐式全局状态。模块、静态字段、全局符号或隐藏缓存可能比业务所有者活得更久。弱引用、容量上限不等于生命周期所有权。不可变常量、纯函数和有明确作用域的对象不是同一问题；依据项目隔离要求判断，不一律定为最高严重度。
2. 未撤销的活跃副作用。监听器、定时器、观察器、子进程、临时文件和后台任务在所有者释放后仍存在。框架已拥有的注册不应重复管理；未托管资源必须有明确且可等待的清理。刻意持久化的业务结果不要求回滚。
3. 消费者未完成，依赖已不可用。沿每个 await 追踪最后一次服务调用、完成事件和持久化写入。停止/取消操作不代表已结算；持有服务引用或提供者的 dispose 最后返回，也不证明底层连接和监听器一直可用。

## 明确顺序

先停止接收新工作，再等待已接收消费者结算，之后排空并释放其依赖资源。新请求拒绝与已有请求完成应分开控制。必须捕获实际 disposer 或实际清理任务；包装一个函数并不会转移已独立注册的资源所有权。

检查消费方单独退出、提供方替换以及上层整体停机。框架可能并行清理兄弟资源，反向注册顺序未必有效。一个清理错误也不能跳过其他必要的取消、结算和释放；错误按项目策略可见。

## 证据与报告

构造可达失败交错及可观察后果，先排除已有同步、明确允许丢弃的语义和可选通知。确定性回归：把消费者暂停在最后一次依赖使用之前，启动释放，证明资源与必要监听器仍可用、释放仍在等待，再放行消费者并断言终态与持久化结果。只断言调用次数或空闲状态释放不够。

报告入口、消费者/资源所有者、紧邻源码、交错、后果、修正和验收证据。按真实影响定级，合并同一根因；模式搜索不代表完整安全审计。框架专有 API 和修补方案以项目实际版本为准。
