# 审查代码变更

先查要求，再评价实现。优先正确性、权限边界、生命周期和必要行为，少量有证据的发现优于大量风格意见。此 Skill 是判断方法，不是完整业务清单。

## 确认对象与要求

1. 明确范围与只读/修复授权。确认真实 base/head、工作区各层及完整差异；PR 改 base 或合并后重建范围。
2. 根据改动路径读取适用 AGENTS、模块契约、架构和业务规则，再读 diff 及必要上下文。相关设计记录是证据，不因与历史记录不同就自动否决新设计。
3. 区分需求来源与本次设计选择：改动中新建的规则、测试或决策记录不能自行证明新抽象必要。

## 审查路径

- **意图与两端契约**：跟踪生产者、所有当前消费者和真实运行入口，包含参数、返回、错误、取消、资源责任与兼容性。检查配置传递最终是否生效。涉及持久化或跨版本协议时，按[兼容证据](../seek-doc/references/lifecycle.md#历史格式与兼容记录存在持久化协议时)分别核对新读旧与旧读新，不能只用结构未变或一个方向通过作结论。
- **状态与失败**：调用 [错误与恢复](../seek-error-handling/SKILL.md)，核对副作用已发生多少、恢复后不变量与报告。捕获异常并继续必须有状态所有者的保证。
- **生命周期与并发**：检查发布前状态、await 期间取消、回调异常隔离、重入前所有权、监听解绑及真正静止的销毁。对应测试使用 [测试可靠性](../seek-test-reliability/SKILL.md)。
- **必要性与边界**：每个新字段、抽象、兼容分支和配置都要有当前需求；优先现有所有者附近的扩展点。只为一个内部消费者新增通用公共 API 时，考虑更窄的私有能力。
- **权限与约束执行**：沿拒绝路径追到实际执行操作，检查直接、替代调用者能否绕过 UI、schema、提示词或包装层。声明限制不等于执行限制。
- **派生与借用状态**：核对权威来源、缓存失效、通知、显示、重放及成功时点，防止保留借用对象或重复状态造成漂移。
- **边界值**：限制要覆盖最终结果含元数据和包装；检查空值、精确上限、单个超大块和多字节文本，不仅检查局部片段。
- **测试证明力**：断言能否捕获预期回归，是否观察外部状态或实际产物；负例通过真实入口失败。覆盖率不是正确性的证明。分别通过的组件测试不证明组合路径正确：沿真实入口追踪解析、校验、记录/序列化、执行、持久化和报告中实际存在的步骤，针对改变了顺序或状态保证的交互补最窄失败样本；不机械枚举无关组合。
- **知识与文字**：公开行为变化同步事实所有者；用 [文档维护](../seek-doc/SKILL.md) 与 [表达标准](../seek-prose/SKILL.md) 审相关文字。UI、模型和工具可见文字按行为变化检查，不当纯格式。

专题示例与反例见 [审查案例](references/review-cases.md)，只阅读当前风险相关内容。

## 报告与反馈

每项给出缺陷、最小位置、触发条件、影响及证据，区分已复现、静态推断和建议。不要只说“可能有问题”；缺证据时列待核实问题，不制造阻塞结论。未检查范围明确说明，不把“没有发现”表述成无缺陷保证。

修复授权不来自 review 本身。收到审查意见时核实后修复或用技术证据回应，不机械认同；最终版本变化后重新评估相关证据。提交 PR 评论、批准或合并需遵守另外的动作授权。
